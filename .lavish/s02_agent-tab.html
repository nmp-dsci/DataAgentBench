DataAgentBench · explorer · plan for a new tab · branch agent-build-v0 · 22 Sep 2026

An Agent tab that shows the system as a graph, lets you call any tool by hand, and replays a trial turn by turn

Today the explorer reads. Runs, Run and Trace pages show what happened; nothing on them lets you touch the agent. This tab adds one route that executes — a tool call, on the read-only role, in the network-off sandbox, never a model unless you flip a switch — and builds three views on it: the system graph, the playground, the replay. Same page, one agent picker, one dataset picker, one trace picker.

agent picker · default champion (v0) graph · 9 tools · 4 backends · click a node playground · POST /api/agent/tools/<name> replay · pick run → trial → re-run a call with a changed input llm_extract · display-only unless DAB_PLAYGROUND_LLM=1 cost of the build: $0 — no model call needed to build or test it

01 · goal

Three questions a visitor should answer on one page — none is answerable today

The Runs pages answer "how good, how expensive". They do not answer "what is this thing", "what does query_db actually do", or "why did trial 3 go wrong at turn 14 — what if the SQL had been different". Those are the three panes of the tab, and the current state on each is nothing.

What is the system?

Now: Fig 2b in the s01 plan, a static picture. The explorer has no page for it; the README has prose.

Tab: the graph, generated from agents/<name>/agent.yaml and the tool server's own schemas, so it cannot drift from the code. Click a node for its config, source path and — for a tool — its JSON schema and a "try it" button.

What does a tool do?

Now: read agent/tools.py.

Tab: a form built from the tool's schema (a textarea for sql / code, fields for the rest), run against the chosen dataset with the same guards a trial has: dab_agent role, 60 s statement timeout, docker --network none, output cut at 10 000 chars.

What happened in a trial?

Now: the Trace page lists every turn and the waterfall; you can read but not act.

Tab: pick a run and a trial; a table of every turn (sent / received, chars, elapsed, error); on any tool row, "re-run with changes" opens the playground pre-filled and shows the original output beside the new one.

04 · the playground

One POST route runs one tool with the trial's own guards; seven of nine tools are safe to expose, one echoes, one calls a model

The trial code already separates the tool body from the MCP wrapper (run_sql, _describe, _read_context, …). The change is to finish that split: a call_tool(state, name, args) dispatcher that both make_tool_server and the API call, so the playground cannot behave differently from a trial. Same ToolState, same cut, same errors.

05 · trace replay

The trace page's spans, as a table you can act on: every turn, what was sent and received, and a re-run button on each tool call

The data is already served: /api/runs/{id}/traces/{key} returns the span tree (shipped yesterday) with inputs and outputs per tool. The replay is a second rendering of it — rows instead of bars — with three additions.

  1. Pickers. Run (from /api/runs, champion first) → trial (its results rows, verdict shown) → the table. Selecting a trace also sets the dataset picker, so the playground targets the right pack and tables.
  2. Rows. One per span: t, turn number, sent (assistant text or tool name + main input, cut to 120 chars, expandable), received (the tool result or nothing for a text turn), chars, elapsed, status. A "tool rows only" toggle, on by default; "failed only" when the trace has errors.
  3. Re-run with changes. On a tool row: opens the playground pane pre-filled with that call's exact input; the panel shows the original output on the left and the new one on the right, with a first-difference marker (line number where they diverge) — not a full diff, the outputs are text tables and the point is "did the change matter".
  4. Graph overlay. While a trace is selected, tool nodes carry calls / errors / p50 ms and the edge weight follows call count; clicking a tool node filters the replay table to that tool.

Not in scope: replaying the model turns. Re-running the agent from turn n would be a trial (a model call on the subscription) and belongs to dab eval, not to the explorer. The replay re-runs tools only.

the refactor, sketched · agent/tools.py

TOOL_SPECS: dict[str, ToolSpec] = {
    "query_db": ToolSpec(
        description="Run read-only Postgres SQL against the dataset …",
        schema={"type": "object", "properties": {"sql": …, "limit": …, "save_as": …}, "required": ["sql"]},
        backend="postgres",
    ),
    …
}

def call_tool(state: ToolState, name: str, args: dict[str, Any]) -> tuple[str, bool]:
    """Run one tool body; returns (output, is_error). The MCP server and the playground both call this."""
    t0 = time.time()
    try:
        out = _BODIES[name](state, args)          # run_sql / _describe / … unchanged
        err = False
    except Exception as e:
        out, err = f"{type(e).__name__}: {e}", True
    state.record(name, args, out, t0, err)
    return cut(out, RESULT_CUT), err

def make_tool_server(state: ToolState) -> McpSdkServerConfig:
    tools = []
    for name, spec in TOOL_SPECS.items():
        async def _fn(args: dict[str, Any], _n: str = name) -> dict[str, Any]:
            out, err = call_tool(state, _n, args) if _n != "llm_extract" else await _call_llm_extract(state, args)
            return {"content": [{"type": "text", "text": out}], **({"is_error": True} if err else {})}
        tools.append(tool(name, spec.description, spec.schema)(_fn))
    return create_sdk_mcp_server(name="dab", version="1.0.0", tools=tools)

08 · risks and failure modes

The tool refactor is the risk; everything else is additive

The refactor changes a trial's behaviour

Mitigation: bodies move, they are not rewritten; the existing tool tests run; a new test calls every tool through both paths (call_tool and the MCP wrapper) with the same args and asserts identical output on the pack-only tools. A smoke re-run (12 × 1, ≈ $2) after the refactor is cheap insurance and is listed as A4.

The explorer now depends on Docker and Postgres being up

Only the playground does. execute_python returns 503 with make sandbox / make db-up in the message; the graph and replay never touch either. The sandbox container starts on the first execute_python call, not at server start, and is removed on shutdown (docker rm -f dab-sbx-playground).

A browser tab can run arbitrary SQL / Python

On a local, single-user explorer, with the trial's own guards: the SQL role cannot write and times out at 60 s; Python has no network and a 600 s cap. This is the same surface the agent already has. The route is not exposed beyond localhost by anything in this repo.

Concurrency in the playground

FastAPI runs sync handlers in a thread pool; two execute_python calls share one container but are separate processes in separate /work keys per dataset — the same as two trials of one dataset would not be, so a playground call for a dataset uses a single key playground_<dataset> and two concurrent calls on the same dataset may read each other's parquet. Acceptable for one person at one screen; noted in the panel.
