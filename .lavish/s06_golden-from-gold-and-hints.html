What the goldens are for

Each golden is the reference path to its answer: the tables, joins, text patterns and filters that work. A challenger's trace can be compared with it query by query (s03's trace-vs-golden step), and a failure now has a concrete "what it should have done". Goldens stay in dataagentbench_meta: never in a prompt, the pack or the curator.

Why the agent fails where SQL succeeds

The spike's notes name concrete causes, and most are teachable without an answer: regex that ignores thousands separators (deps_dev_v1/2), 1 of ~100 sentence templates parsed (patents/2), ILIKE '%x%' joins that match the wrong row, whole-day rounding that makes ties (crmarenapro/9), one date format of three (googlelocal/4), and llm_extract where a regex reads the template exactly.

01 · the method you proposed · written down so it can be repeated

Gold as the target, hints as the join path, the run's SQL as the start: check each CTE against the gold before adding the next

  1. Start from the run's SQL. The Golden editor seeds from the champion's last error-free query_db call. Here that is the versioned_releases query: the latest NPM release per Name by Ordinal, joined to project_packageversion, with no stars yet.
  2. Check the gold is in it before building on it. Join the gold rows (as values) to the CTE. If a gold row is missing, the CTE's filter is wrong, and nothing added later will fix that. Here all five are present with rn = 1.
  3. Follow the hints for the join. System + Name + Version into project_packageversion, then ProjectName into project_info. Join on the exact owner/repo, never ILIKE '%name%' (§2, step 3).
  4. Parse the text column in SQL. Survey every phrasing, count what each regex reads, and name what stays unread. No Python.
  5. Rank, then judge with the real route. POST /api/golden/<ds>/<n>/run runs as the agent's role and returns the validator's verdict plus the gold match (exact, reordered or differs).
  6. When it isn't exact, explain why before changing anything. Every difference is either a bug in the SQL or a property of the gold. Only the first is fixed; the second is recorded in the proposal's note. The gold's values never go into the SQL as literals.

step 3 · the trap in the champion's join

ILIKE '%ProjectName%' gives 36 of 2,450 releases the wrong star count

The champion joined with "Project_Information" ILIKE '%' || "ProjectName" || '%'. A short name matches inside longer ones: microsoft/typescript also matches microsoft/typescript-website, and tj/co picks up a bigger tj/co… project. Of the 2,450 latest releases with a project, 122 match more than one info row and 36 end up with a different star count (e.g. …>co 11,862 → 25,437). None of the 36 passes 57,779, so the top 5 survives here by luck. Joining on the parsed owner/repo, ps.project = lower(ppv."ProjectName"), is exact.

04 · the golden SQL · loaded as proposal #30, not saved

One statement, three CTEs on the hints' path, and a tiebreak stated in a comment

A · five rows · validator: pass · gold match: differs (row 5 of 5, a tied package) · 828 ms

-- deps_dev_v1/1: the 5 latest NPM releases whose GitHub project has the most stars
with versioned_releases as (       -- the latest release of each NPM package (highest Ordinal)
  select pi."Name", pi."Version",
    row_number() over (partition by pi."Name"
      order by (pi."VersionInfo"::jsonb->>'Ordinal')::int desc nulls last) as rn
  from deps_dev_v1_packageinfo pi
  where pi."System" = 'NPM' and pi."VersionInfo"::jsonb->>'IsRelease' = 'true'
),
project_stars as (                 -- owner/repo and stars, read from the free-text Project_Information
  select lower(substring("Project_Information" from '([A-Za-z0-9_.-]+/[A-Za-z0-9_.-]*[A-Za-z0-9_-])')) as project,
    replace(coalesce(
      substring("Project_Information" from '(?i)stars? count of ([\d,]+)'),   -- "a stars count of 57779"
      substring("Project_Information" from '(?i)starred by ([\d,]+)'),        -- "starred by 1835 users"
      substring("Project_Information" from '(?i)([\d,]+) stars?\M')           -- "73,499 stars"
    ), ',', '')::bigint as stars
  from deps_dev_v1_project_info
),
release_stars as (                 -- hint: match on System, Name, Version, then ProjectName -> project_info
  select vr."Name", vr."Version", max(ps.stars) as stars
  from versioned_releases vr
  join deps_dev_v1_project_packageversion ppv
    on ppv."System" = 'NPM' and ppv."Name" = vr."Name" and ppv."Version" = vr."Version"
  join project_stars ps on ps.project = lower(ppv."ProjectName")
  where vr.rn = 1
  group by vr."Name", vr."Version"
)
select "Name", "Version"
from release_stars
order by stars desc, "Name" desc  -- 95 lodash/lodash packages tie at 5th (57779 stars); Name desc picks one
limit 5

§5b · our loader drops 38 stockmarket tables from stocktrade_all

load.py:253 builds the union table from the largest group of per-ticker tables with identical column types. 2,715 tickers have Volume bigint; the 38 with Volume double precision (SDOW, FTFT, FTR …) are left out, yet the pack describes the table as the whole family. That alone cost the champion stockmarket/2 and /3. The fix is to group by column names and widen the types (bigint → double). It changes what the agent queries, so it's a re-load plus a re-baseline, and it's decision D25 below.

Gold and validator problems the spike found

  • pancancer_atlas/1 (0 of 270): the gold groups by the ICD-O-3 code, while the question's "histology types" reads as the text column.
  • github_repos/2: the validator needs 21 characters around an 18-character answer, so a bare correct answer always fails.
  • deps_dev_v1/1, /2: a tie and version picks that no column reproduces.
  • stockmarket/2, yelp/4: gold names spelled differently from the data.
  • agnews/1–4: the answers need an article category the database doesn't hold. The released benchmark expects an LLM step here.
  • Fixed in our code: match_gold called an empty result "reordered" against a single-line gold. It now reads "differs", with a test.
