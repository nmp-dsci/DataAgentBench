system.md · draft, 1.5 KB against the champion's 2.9 KB

You answer one question about one dataset by writing SQL.

## The data
Every table in the Tables list is loaded into one Postgres 16 schema and named <dataset>_<table>. The database description below was written for the original stores (SQLite, DuckDB, MongoDB): ignore the storage format, use the Postgres names from the Tables list, and write Postgres SQL. Quote mixed-case columns ("Name").

## How to work
1. Read the description and the hints. Map every part of the question to a table and a column before you query.
2. Explore with small queries (LIMIT, counts, distinct values). Free text is generated from a few templates: survey a column's phrasings over the whole table and count what your pattern reads before you trust it.
3. Build the answer as ONE SQL statement. Use CTEs for steps; regex (substring(s from 'p'), regexp_match, split_part) for text; to_timestamp for dates stored as text; joins on exact keys, never ILIKE '%x%' where a key can be extracted. Read literally: "more than" is strict. Rankings need a tie-break.
4. Finish with submit_answer(sql, answer, mode):
   - sql: the final statement. Its result must contain the answer.
   - mode "pass_through" (prefer it): the answer IS that result; the harness re-runs sql and renders it. Name the columns as the question names them.
   - mode "derived": the answer needs one step after the SQL (reading the returned text to reach a verdict, choosing between returned rows). Give the answer and describe the step in one line.

output · submit_answer(sql, answer, mode, step?) replaces return_answer(answer)

  • sql: the one final statement. The harness re-runs it as dab_agent (read-only, 60 s) and stores the columns, rows and rendered text, so the agent's result is known exactly, not as the model retold it.
  • mode: "pass_through": the scored answer is the rendered result, the same render() a golden gets. Most questions: 43 of the 49 goldens pass their validator as the plain rendered result (github_repos/2 needs its header).
  • mode: "derived" (+ step, one line): the model writes the answer from the returned rows. This is the post-processing the question asked about, and it needs no Python: the judgment questions (crmarenapro/1, 2, 3, 6, 7: read the returned transcript, name the violated policy), or choosing among a few returned candidates. step says what was done so a diagnosis can tell "SQL wrong" from "reading wrong".
  • Recorded per trial in results.jsonl and the trace: agent_sql, agent_result (rendered), mode, step, answer, and the validator verdict as now.

The scorecard: every question scored three times, and the combination says what to optimise

Every run scores all 54. Each question is run and gets an answer verdict, golden or not, so the run stays comparable with the champion and the leaderboard. SQL and decision are scored against the golden, so they exist only where a golden does (49 of 54 today); the other 5 (agnews/1–4, crmarenapro/7) read "no golden" in those columns, still count in the answer total, and are left out of the optimisation loop until someone writes their golden.

Answer · pass / fail

The question's own validator on the submitted answer. Unchanged from today: this is the number on the leaderboard. Denominator: 54.

SQL · pass / fail

The agent's SQL result against the golden's result, with the gold match's cell rules (case, float noise): pass when it recreates the golden result (same rows, any order). For an evidence golden, pass when the agent's result contains the golden's evidence rows. Two different SQL texts that return the same rows both pass; the structure diff only explains a fail. Denominator: questions with a golden.

Decision · pass / fail

Did the agent choose the right mode? The golden says which is right: an answer golden means the result is the answer, so pass_through is right; an evidence golden (a judgment question) means derived is right. Denominator: questions with a golden.

The optimisation loop, one turn

Run the challenger on a train split. For each failure, the diagnosis gives a category and the evidence (result diff, SQL structure diff). The optimiser proposes one edit to system.md (or a pack file) that targets a category, never a question. Re-run the train split, then a held-out split; accept only if held-out pass@1 rises and nothing regresses. That is s03's loop with SQL-level evidence.

Risks

  • Confounded comparison: hints on, pack off, tools cut and the contract change all at once, against v0's existing run (hints off). Accepted: v0 is never re-run (too expensive), so the gain is the build as a whole, not per change.
  • Leakage: an optimiser that sees golden SQL can write answers into the prompt. Guards in D29.
  • Shape: a pass-through answer is the bare rendered result; github_repos/2 showed one validator can reject an exact bare value. The harness uses plain render() (never the gold's shape), so such cases show as "format".
  • Lost ground: agnews (0 of 4 now) stays 0; nothing else needs Python.

The isolation rules (an empty working directory, a strict MCP config, the init check), the read-only dab_agent role, the 54 questions, the validators and the rescore. A run folder stays the record and MLflow the index. The Runs tab compares the challenger with the champion as any version.

The optimiser: specification

It fits how prompts are already built: one system prompt per dataset, composed from a shared system.md and that dataset's own blocks. The optimiser writes a new per-dataset block, dataset notes, from that dataset's failed train questions. It never writes to a question.

agent · agents/optimiser/ (a sibling of agents/curator/)

Modelsonnet → claude-sonnet-5 (agent/llm.py, the one place a model is named), effort medium, on the subscription (require_live()).
SessionsOne per dataset with at least one failed train question, run in parallel (up to 11; agnews has no golden, so no session). Each is isolated exactly like a trial: an empty directory, no CLAUDE.md or memory, a strict MCP config, the init check.
Toolsquery_db (read-only, as dab_agent): to check a claim against the data, e.g. survey a text column's phrasings before recommending a pattern. write_notes(notes, rationale) ends the session.
Budgetmax_turns: 20, 600 s per session. About $2–4 for a round of 11 sessions, going by the curator's $1.40 for 12 one-turn Sonnet sessions.
Commanddab optimise <run> --into v2_sql: copies v1_sql, writes the notes, sets challenger_of: v1_sql, registers the prompt version in MLflow.

what one dataset's session sees

  • What the agent saw: system.md, the tables map, db_description.txt, hints.txt and the current notes (empty for v1).
  • Each failed train question of that dataset: the question text, the scorecard (answer / SQL / decision), the category, agent SQL beside golden SQL, the result diff, the mode and step, and a trace summary (tool calls, errors, turns).
  • Each passing train question of that dataset: its agent SQL, so the notes don't break what already works.
  • Never: held-out questions (16 of 49), other datasets' questions, or the gold answer text of a question that has no golden.

01 · the method you proposed · written down so it can be repeated

Gold as the target, hints as the join path, the run's SQL as the start: check each CTE against the gold before adding the next

  1. Start from the run's SQL. The Golden editor seeds from the champion's last error-free query_db call. Here that is the versioned_releases query: the latest NPM release per Name by Ordinal, joined to project_packageversion, with no stars yet.
  2. Check the gold is in it before building on it. Join the gold rows (as values) to the CTE. If a gold row is missing, the CTE's filter is wrong, and nothing added later will fix that. Here all five are present with rn = 1.
  3. Follow the hints for the join. System + Name + Version into project_packageversion, then ProjectName into project_info. Join on the exact owner/repo, never ILIKE '%name%' (§2, step 3).
  4. Parse the text column in SQL. Survey every phrasing, count what each regex reads, and name what stays unread. No Python.
  5. Rank, then judge with the real route. POST /api/golden/<ds>/<n>/run runs as the agent's role and returns the validator's verdict plus the gold match (exact, reordered or differs).
  6. When it isn't exact, explain why before changing anything. Every difference is either a bug in the SQL or a property of the gold. Only the first is fixed; the second is recorded in the proposal's note. The gold's values never go into the SQL as literals.

One statement, three CTEs on the hints' path, and a tiebreak stated in a comment

A · five rows · validator: pass · gold match: differs (row 5 of 5, a tied package) · 828 ms

-- deps_dev_v1/1: the 5 latest NPM releases whose GitHub project has the most stars
with versioned_releases as (       -- the latest release of each NPM package (highest Ordinal)
  select pi."Name", pi."Version",
    row_number() over (partition by pi."Name"
      order by (pi."VersionInfo"::jsonb->>'Ordinal')::int desc nulls last) as rn
  from deps_dev_v1_packageinfo pi
  where pi."System" = 'NPM' and pi."VersionInfo"::jsonb->>'IsRelease' = 'true'
),
project_stars as (                 -- owner/repo and stars, read from the free-text Project_Information
  select lower(substring("Project_Information" from '([A-Za-z0-9_.-]+/[A-Za-z0-9_.-]*[A-Za-z0-9_-])')) as project,
    replace(coalesce(
      substring("Project_Information" from '(?i)stars? count of ([\d,]+)'),   -- "a stars count of 57779"
      substring("Project_Information" from '(?i)starred by ([\d,]+)'),        -- "starred by 1835 users"
      substring("Project_Information" from '(?i)([\d,]+) stars?\M')           -- "73,499 stars"
    ), ',', '')::bigint as stars
  from deps_dev_v1_project_info
),
release_stars as (                 -- hint: match on System, Name, Version, then ProjectName -> project_info
  select vr."Name", vr."Version", max(ps.stars) as stars
  from versioned_releases vr
  join deps_dev_v1_project_packageversion ppv
    on ppv."System" = 'NPM' and ppv."Name" = vr."Name" and ppv."Version" = vr."Version"
  join project_stars ps on ps.project = lower(ppv."ProjectName")
  where vr.rn = 1
  group by vr."Name", vr."Version"
)
select "Name", "Version"
from release_stars
order by stars desc, "Name" desc  -- 95 lodash/lodash packages tie at 5th (57779 stars); Name desc picks one
limit 5

§5b · our loader drops 38 stockmarket tables from stocktrade_all

load.py:253 builds the union table from the largest group of per-ticker tables with identical column types. 2,715 tickers have Volume bigint; the 38 with Volume double precision (SDOW, FTFT, FTR …) are left out, yet the pack describes the table as the whole family. That alone cost the champion stockmarket/2 and /3. The fix is to group by column names and widen the types (bigint → double). It changes what the agent queries, so it's a re-load plus a re-baseline, and it's decision D25 below.

  • pancancer_atlas/1 (0 of 270): the gold groups by the ICD-O-3 code, while the question's "histology types" reads as the text column.

  • deps_dev_v1/1, /2: a tie and version picks that no column reproduces.
  • stockmarket/2, yelp/4: gold names spelled differently from the data.
  • agnews/1–4: the answers need an article category the database doesn't hold. The released benchmark expects an LLM step here.
  • Fixed in our code: match_gold called an empty result "reordered" against a single-line gold. It now reads "differs", with a test.
