03 · round 2 · the method

03 · Round 2 — a ledger says where each statement broke, and the optimiser writes an SQL playbook across datasets

Three changes to the loop, in the order they run. A reader turns every golden and every submitted statement into seven lines of words (the ledger), so the diagnosis is "the parse broke: the golden reads three phrasings, the agent one" instead of "join differs". The optimiser gets component sessions that read every failed training question where that component broke, across all datasets, and write one section of a playbook in system.md: how to discern what the question needs at that step and how to write it in Postgres. The generator is told to plan before it queries, in the same seven lines, and the plan is recorded so a later diagnosis can tell "misread the question" from "mis-wrote the SQL".

The seven components: what the question asks, what the statement carries, and where round-1's failures sit

The same seven names are used everywhere: the ledger's lines, the playbook's sections, the generator's plan, the tab's matrix. They are in the order a statement is built, so "the first component that differs" is a well-defined place.

the ledger · eval/ledger.py · new · runs in dab diagnose

  • One reader call per statement. Input: the question, the statement, the tables it names. Output: seven lines of at most 30 words, technique only, no values. Sonnet 5 at medium; about 49 golden lines (cached by golden id in dataagentbench_meta.golden_ledger) plus 49 agent lines per run (in scorecard.json).
  • One comparison call per question: golden lines beside agent lines, a verdict per component (same · differs · absent) and the first that differs. The category becomes that component; sqlglot's sets stay as the mechanical cross-check under it.
  • Never in a prompt. The ledger lives beside the run and the golden; the guard is not needed on it, only on what the optimiser writes from it.
  • Cost: about 100 short calls, roughly $1 per dab diagnose --refresh; the golden half is paid once.

the generator · plan first · agents/v3_sql/system.md + agent/tools.py

  • "How to work" gains one step: before the first query, write the plan as the seven lines; then build the CTEs in that order; then submit.
  • submit_answer gains plan (the seven lines, required). It is recorded on the trace and shown on the trial page beside the golden's ledger, so the round can see whether the agent misread the question or mis-wrote the statement.
  • The playbook is the method part of system.md: a fixed skeleton of seven headed sections that the component sessions fill; the "How to work" list above it stays.
  • Budget: system.md grows from 2.7 KB to about 5 KB; the cap moves from 3,000 to 5,000 characters. Dataset notes' cap 1,500 → 2,000, since the cap, not the guard, did the refusing.

agents/v3_sql/system.md · the playbook skeleton the component sessions fill (each section ≤ 600 chars)

## From the question to the statement
Write the plan first, one line per step, then build the CTEs in this order.

### 1 · sources — what the question names and where each thing lives
(the section the `sources` session writes)
### 2 · keys — how the rows match, and what each side needs first
### 3 · parse — what must be read out of text or JSON, and every template it comes in
### 4 · filter — every condition, read literally, with its window
### 5 · metric — what is measured, at what grain, by what formula
### 6 · rank — the order, the tie-break, the limit
### 7 · shape — the columns the question names, one row or many, the mode

agents/optimiser/component.md · the new session prompt, in short

You maintain one section of the SQL playbook an SQL-answering agent reads: the "<component>" step of going from a question to a statement.

You see every failed training question, across datasets, where this component is the first to differ from the reference: the question, the ledger's two lines for this component (reference vs agent, in words), both statements, the result diff.

Write the section as general instructions: how to discern what the question needs at this step, and how to write it in Postgres. Never a dataset fact (those belong in dataset notes), never a question, a value, or copied reference SQL. Check a claim with query_db before you make it. At most 600 characters.

Call write_section(text, rationale) once; a refusal names what to fix; a second leak refusal drops the section.

D32 · at what level the optimiser reads and writes

The user's question: per dataset, or "see all the failed questions and generalise". The evidence (Fig 1, Fig 2) says both are needed, in different files.

A · per dataset only (round 1)

10 sessions, dataset notes, a thin system pass

Keeps the code as is; the briefing is led by the ledger instead of sqlglot. Expect more of round 1: facts that fix what was read. Cost ≈ $1.3. Risk: held-out SQL stays near 2 of 16, because nothing teaches the method.

B · components across datasets + datasets recommended

≤ 7 component sessions write the playbook; dataset sessions write facts

Each component session reads every failed train question where that component broke, from every dataset, so a lesson seen three times is written once, as method. Dataset facts stay where they are useful. Cost ≈ $3 (component briefings are larger, 30–60 KB). Risk: a playbook section that is too general to change behaviour; measured on held-out SQL.

C · one session over every failure, system.md only

Maximum generalisation, no dataset notes

One Sonnet session reads all 21+ failures and rewrites system.md. Simplest, but it drops the facts that lifted github_repos 1 → 3 and crmarenapro 6 → 7, and one session with 100 KB of failures checks little against the data. Cost ≈ $0.8.

risks

  • Sixteen held-out questions. ±2 is noise; McNemar is reported, not a gate. A round that moves held-out SQL by 3 or more is the first real signal.
  • "Differs" is not "wrong". The golden is one person's way; the ledger explains a fail, it does not define one. The SQL verdict stays result-based (the re-run statement returns the golden's rows).
  • A fifth model caller. The reader sees goldens and gold answers. It runs only in dab diagnose, writes words with no values (a test asserts it), and nothing it writes enters a prompt; the guard still checks what the optimiser writes from it.
  • A longer prompt for Haiku. system.md about doubles. If v3's trials cost more than v2's $4.51 by a third or turn counts rise, the playbook is too long; the caps come down.
  • Caps up, leak surface up. 2,000 and 5,000 characters give the guard more text to check; the rules are unchanged and the drop rule still ends a session on a second leak.
  • Five questions stay outside (agnews/1–4, crmarenapro/7): no golden, answer-scored only, as today.
