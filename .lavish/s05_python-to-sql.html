Fact 1 · six phrasings, one position

Every description names its languages as Name (N bytes) after one of six openers ("The codebase includes:", "The majority of the code is in", "This repository is mainly written in", "While most of the project is built in", "Nearly all of the code is in … totaling N bytes", "This project is built entirely in"). The trial's Python knew five of the six. The rule "what follows the first in or : " parses 2,957,293 of 2,957,293 descriptions that name a language; 368,341 say "No language information available."

Fact 2 · first listed is largest

So "main language" needs no byte comparison: in 0 of 69,647 sampled repos was the first-listed language not the largest. Names can be lowercase ("Vim script", "sed") or contain " in " ("Ragel in Ruby Host", 15 rows), which is why the pattern anchors on the opener, not on capital letters.

Fact 3 · no language row, no main language

torvalds/linux has the most commits (16,061) but no row in the languages table, and the gold leaves it out. An inner join does the same, so "not Python" means "known, and not Python".

golden SQL · github_repos/4 · passes · recreates the gold exactly · 374 ms

with commits as (
  select repo_name, count(*) as num_commits
  from github_repos_commits
  group by repo_name
),
langs as materialized (              -- the six repos' rows first, so the regex runs 6 times, not 3.3M
  select repo_name, language_description
  from github_repos_languages
  where repo_name in (select repo_name from commits)
),
main as (
  select repo_name,
         substring(language_description
                   from '^.*?(?: in|:) (.+?)(?: \([\d,]+ bytes|, totaling)') as main_language
  from langs
)
select c.repo_name, c.num_commits
from commits c
join main m using (repo_name)       -- no language row (torvalds/linux) = no main language: left out
where m.main_language <> 'Python'
order by c.num_commits desc
limit 5
then paste it in /golden/github_repos/4, Run and check, Save as golden

The trap it avoids: 31 s against a 60 s limit

The first version put the regex in a plain CTE. Postgres pushed the <> 'Python' filter down into the scan, so the regex ran on all 3,325,634 language rows before the join cut them to six: 31,067 ms. as materialized forces the six rows first: 374 ms. The whole dataagentbench schema has 2 indexes, none on repo_name; the 480 MB languages table is a sequential scan every time.

Validator: "All repo names matched with fuzzy tolerance." Gold check: "all 6 gold line(s), in order", the header repo_name,num_commits included, because the columns are named as the gold names them.

Postgres regex, for the rest of the rollout: substring(s from 'p') (first group), regexp_match (all groups, first match), regexp_matches(s,'p','g') (every match, as rows), regexp_substr / regexp_count (PG 15+; the server is 16.14). Word boundaries are \m / \M, not \b.

03 · diagnosis · why the agent reached for Python

Four habits, each fixable in the prompt or the pack, none in the data

1 · It assumed parsing needs Python

Sampled a templated column, then wrote re.search in pandas. Nothing in the prompt says Postgres has substring … from, regexp_match and regexp_split_to_table, or that the text is generated. Fix: the SQL-first rule plus a five-line Postgres regex and date cheat sheet (the c08-sqlonly challenger in s03).

2 · save_as invites a pandas pipeline decided: no Python

Once a result is parquet in /work, the next step is pd.read_parquet. In github_repos/4 the agent saved three results and merged them in Python, instead of one statement with CTEs. Fix (your call): remove Python. The SQL-first belt drops execute_python and save_as together; intermediate results become CTEs in the one statement, as every proposal in §4 is written.

3 · The pack does not describe text columns

The agent rediscovered each template by sampling 10 rows, and its regexes covered five of the six phrasings. The context build (code, never a question) can survey every text column the way §1 did (templates, counts, a tested extraction pattern) and write it into the pack. That is the legitimate version of "the answer is in the data".

4 · Mixed date formats

yelp and stockindex store dates in three to five shapes (2016-01-29 00:00:00, 29 May 2013, 23:01, August 01, 2016 at 03:44 AM); the agent reached for to_datetime with a format list. SQL does it with a case on the shape and to_timestamp, and the pack can list the shapes per column.

Performance goes with it: an all-SQL agent will write regex over big tables. Teach "cut rows first, regex last" (as materialized), and consider indexes on the join keys at load time: the schema has 2 indexes today.
