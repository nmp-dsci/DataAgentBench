A public project that ingests the DAB benchmark and opens an explorer over every question, its gold, and who has beaten it

DataAgentBench (DAB, UC Berkeley + Hasura PromptQL) is a data-agent benchmark: natural-language questions over several databases at once, each with a ground-truth answer and its own validate.py. This build stands the project up as a sibling of DABStep-loop: a Python package that ingests the benchmark's text layer, a FastAPI index, and a React explorer for the datasets, questions, gold answers, validators and published trials. Agents, evals, the loop and optimisation come in later builds on the same skeleton.

verified from source: 17 datasets · 104 queries · 104 gold · 104 validators · 54 on the leaderboard proposed: public repo nmp-dsci/DataAgentBench, gh is logged in as nmp-dsci, name is free proposed: React + Vite + FastAPI on tokens.css, uv, Python 3.12, same skeleton as DABStep-loop this build: scaffold · ingest · index · explorer · rescore of the published trials proven this session: 14,210 answers judged by the 54 validators · 3 queries never passed decided: the 54 leaderboard queries only; the 50 unreleased are deferred to a later build decided: ingest A (text layer only) · commit the index and answer files with attribution · approved M0–M4, 2026-09-20

1 · Goal — open the app, see the 54 scored questions, their gold, and who has beaten them

Done for this build means make setup && make upstream && make ingest && make dev opens a local explorer over the 54 leaderboard queries where you can pick any of the 12 datasets, read every question with its gold answer and validator side by side, see the schema description and the hint file, and see how the published agents did on it. 03 · what "has golden evals" means here

3 · Gold — every query has gold; the validator is the eval, the CSV is often a copy

All 104 queries ship a ground_truth.csv and a validate.py, so "which have gold" is not the question; with the 50 deferred, the 54 in scope all have gold too. The useful distinctions are how a query is judged and whether anyone has published a run against it. Only 20 of 104 validators read the CSV at all; 84 carry the answer inline in Python, and in three cases the two disagree in kind (PATENTS q1 lists 73 CPC codes in the CSV and the same 73 hard-coded in the validator; DEPS_DEV_V1 q1's revised validator accepts any of 95 tied packages while the CSV records one).

Validator styles across the 104 (the 54 in scope in the second column) · classified by reading every validate.py this session (3,553 lines in total)
StyleQueries · in scopeHow it judgesWhere the gold livesWhat it costs to run

substring / list membership12 · 12case-insensitive containment; some require every list item, one (googlelocal q1) requires orderinlinemicroseconds
levenshtein9 · 9fuzzy match of each gold name against the answer via common_scaffold.validate.levenshtein, a pure-Python O(n·m) DPinlineseconds to minutes: answers reach 13,798 characters and PATENTS q1 has 73 names

The levenshtein row is why a naive "validate everything" script did not finish in two minutes this session: re-scoring must run in a worker pool with a per-call timeout and cache to disk (§7).

04 · decision A · what to pull in

4 · Ingest — the text layer is 322 KB; the databases are 13.4 GB and can wait

Everything the explorer shows is text: 54 × (query.json, ground_truth.csv, validate.py), 12 × (db_description.txt, db_description_withhint.txt, db_config.yaml), the manifest, the rubric, 9 answer files (4.6 MB) and the site's two JSON files (52 KB). A shallow clone with GIT_LFS_SKIP_SMUDGE=1 brings all of it down in seconds and leaves every .db as a 130-byte LFS pointer, which is itself useful: the manifest gives us size and sha256 per file without downloading one.

recommended

A · Text layer only

What: make upstream shallow-clones with LFS skipped into data/upstream/ (gitignored); make ingest writes data/index/*.json.

Cost: ~300 MB clone (git history of the answer files), zero database bytes, no Postgres or Mongo.

Gives up: live schema previews and row counts; the explorer shows the authors' db_description.txt instead, which is what agents see anyway.

B · Text layer + the small databases

What: A, plus make data SMALL=1 pulls the 25 manifest files under 50 MB (about 124 MB) from the Hugging Face mirror, verified by sha256, so sqlite and duckdb schemas can be introspected in-app.

Cost: 124 MB local, a duckdb and sqlite3 dependency, one more page. Postgres dumps (.sql) and Mongo dumps (.bson) still need servers, so coverage is partial (7 of the 12 datasets fully).

C · Everything now

What: the full 13.36 GB via download.sh, plus Postgres 17 and MongoDB 8 running locally, per the README.

Cost: hours of download (8.35 GB for the 54), 5.4 GB for PATENTS alone, two servers to keep alive, all for a build that never runs an agent. This is the agent build's job (M5), gated per dataset: make data DATASET=bookreview.

decided · decision A

Option A: the text layer only; databases wait for the agent build

Approved in review on 2026-09-20. make upstream is a shallow clone with LFS skipped; no database byte is downloaded in this build.

05 · architecture

5 · Architecture — one package, one ingest, one JSON index, one API, one SPA

The shape is DABStep-loop's, minus the agent and loop planes, so that those planes slot in later without moving anything. The index is files first: make ingest is deterministic and its output is committed, so CI, the frontend and a future demo image never need the upstream clone.

The index records, and the one key that joins everything

queries.json[i] = {
  "id": "crmarenapro/1",           ← dataset_key + "/" + query number
  "dataset_key": "crmarenapro",     ← folder name lower-cased
  "query_id": 1,
  "question": "...",                ← query.json verbatim
  "gold_text": "Authority",         ← ground_truth.csv verbatim
  "gold_lines": 1,
  "validator": { "style": "substring", "lines": 27,
                 "reads_gold_file": false, "source": "..." },
  "released": true,                 ← always true in this build; the ingest
                                    filter that a later build relaxes
  "footnote": null,                 ← leaderboard.json sources[] when revised
  "trials": { "files": 9, "n": 405, "passed": 301 }   ← from rescore
}

What each plane owns

  • data/ — upstream.py (clone, verify the commit), ingest.py (walk folders, classify validators, apply aliases, write the index), manifest.py.
  • eval/ — validators.py loads a query's validate.py in a subprocess with common_scaffold on the path and a timeout; rescore.py runs the pool and writes trials.json. This plane is reused unchanged when our own agent produces answers.
  • serving/ — FastAPI reading the index at startup; serves frontend/dist as the SPA fallback, exactly like DABStep-loop.
  • cli.py — Typer: dab upstream, dab ingest, dab rescore, dab serve, dab stats (prints the §1 numbers, which the README quotes).

  • Three released queries have never passed in 265 trials each: agnews/3, pancancer_atlas/1, patents/1. Fifteen pass under 10%. Two pass at 95% or more (crmarenapro/1 265/265, stockmarket/1 262/265).
  • The correction: the micro rates above are not the site's Pass@1. The site takes the mean over datasets of each dataset's mean per-query rate (a macro average), which is why react_gemini-3-pro reads 48.6% here and 0.4546 there. rescore.py reports both and the M4 test compares the macro figure.
  • Cost: the naive single-process run took over ten minutes, almost all of it in the nine levenshtein validators; the pool-and-timeout design in the steps below is not optional.
  • Not yet included: the Opus 4.6 file in leaderboard_submissions/ (270 rows), which brings the total to 14,480 for M4.

How the rescore runs, given the levenshtein cost

  1. Group the 14,480 rows by (dataset_key, query_id) via the alias map; unmatched rows are counted and reported, never dropped silently.
  2. For each query, spawn one worker with data/upstream on sys.path, import its validate.py once, and judge its rows; signal.alarm(30) per call, a timeout counts as a fail and is flagged timed_out.
  3. Write data/index/trials.json: per query per file, n, passed, timed_out, and up to three pass/fail example row ids; write the full per-row verdicts to data/index/verdicts.jsonl (gitignored if over 5 MB).
  4. A test asserts the recomputed per-dataset means match the site's baselineStratified and promptqlStratified tables to two decimals, so the vendored validators are proven before any number ships.

What the explorer will and will not claim

  • Will: per-query pass rate per answer file with its denominator; the best single file per query; the footnote for revised gold.
  • Will not: an overall Pass@1 for an agent from partial files, a "difficulty" label with no trials behind it, or anything at all about the 50 deferred queries beyond their count.
  • Caveat carried on the page: the site re-scored on 2026-06-12 under then-current validators; ours runs under the validators at commit 0290945, so a small difference on DEPS_DEV_V1 q1 is expected and the test tolerates it on that one query.

Conventions carried over, and one not

  • Python 3.12, uv, ruff, mypy strict, pytest — the workspace's rules; make lint and make test are green before the first push.
  • Frontend on tokens.css with the design lint that fails on any hex outside the token block; three type voices; assertion headlines; no Tailwind.
  • Files first — the index is committed, so git clone && make setup && make dev works with no network call to upstream.
  • Not carried yet: the App Runner deploy, MLflow, the billing guard and the demo image. They belong to the agent build and are listed in §9 so the skeleton leaves room.
  • Attribution — README.md and data/index/ATTRIBUTION.md name the paper (arXiv 2603.20576), the repo, and the source commit hash the index was built from; make ingest refuses to run against a dirty or unknown upstream commit.
