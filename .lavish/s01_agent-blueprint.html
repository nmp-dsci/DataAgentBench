01 · goal

1 · Goal — one question from every dataset first, measured and compared, then all 54, then five trials each

Done for the smoke means make data && make context && make eval AGENT=v0 SPLIT=smoke runs one Claude Agent SDK agent (Haiku 4.5, effort medium) on one question from each of the 12 datasets, the benchmark's own validators judge each answer, the run opens in the explorer beside the published rows for those 12 queries, and dab runs profile prints the measured tokens per turn. Then the same agent on all 54 × 1, then 54 × 5, which installs v0 as the champion (§11); v1 is what the loop promotes over it in the next build. The build is a sequence of compared runs, not one shot; the loop is the build after it.

02 · the reference agent

2 · Reference — the benchmark hands the agent its dataset, four tools and a text description; nothing else

Everything below is read from data/upstream/ at commit 0290945. The reference scaffold is what produced the five react_* baseline files and the Opus 4.6 row we rescored; it is the floor, and its gaps are where the leaderboard teams found their points.

How a trial starts

run_agent.py --dataset crmarenapro --query_id 3 --llm claude-opus-4-6 --iterations 100 --use_hints. The dataset picks query_<DS>/; db_description.txt (and with the flag, db_description_withhint.txt) is read once and pasted into the user prompt; db_config.yaml is handed to the tools. The agent never sees a file path, only logical names like books_database.

The dataset is known upfront by design. The user prompt is literally QUERY: … DATABASE DESCRIPTION: …. The paper: "database descriptions and hints are dataset-level and remain unchanged across queries within the same dataset."

What the agent cannot do

No schema tool. list_db returns table names; column names exist only in the description text. Mongo find only, default limit=5, no aggregation pipeline. No row cap on SQL — a big result is dumped to a JSON file and the model sees the first 10 000 chars. Postgres and Mongo are loaded from dump on every trial (createdb + psql -f, mongorestore) and dropped after.

The system prompt's rule 1 is "Always use tool calls. Do not output plain text" — and a plain-text turn is silently taken as the final answer (DataAgent.py:310).

Using it is "Hints ✓" on the leaderboard; all but three rows do. Camber (#3) was audited as never reading it and still scored 0.879 — its per-dataset prompts encoded the same facts by hand.

Why not just imitate the leader? We imitate the stack, not the last step. Everything from 0.56 to 0.91 is a general mechanism and v0/v1 carries all of it: live introspection (Phoenix), an independent verify (Spacedock), the answer contract and literal-reading rules (Alkera), assertions before answering (Sentinel), a per-dataset profile with pitfalls (Camber), measured join overlaps and LLM extraction for text columns (Scout). Permute EQ's extra +0.04 comes from a per-query evidence table built ahead of time and five prompt variants, some query-specific — that is the work of answering the 54 questions offline and handing the executor the result. It does not generalise to a 55th question, it is what the rubric's "tuned prompt" flag exists to mark, and it is where a reviewer reads test-set tuning. The generalisable half of Permute's idea — precomputed evidence per dataset, queried through one tiny tool — is exactly the context pack plus joins.md in §6, and the small executor with one query_db is why D6 picks one dialect. Target: Scout's shape (≈ 0.90) on Haiku, generically; the gap to 0.95 is deliberately left on the table until the smoke and the 54 × 1 pass say where v1's addendum should go.

04 · your two questions

4 · Two questions — the dataset is given, and it is one agent with twelve context packs

Q1 · Does the agent triage which dataset it is in?

No — and it should not. The benchmark states the dataset per query (--dataset is required; the rubric's legitimate prompt inputs are exactly the query text, db_description.txt and the hints file). No leaderboard row triages. A triage step would be a self-imposed problem the score never rewards and the walls never forgive.

What your instinct was pointing at is real, though: the agent needs a knowledge base it reads before it writes SQL, because the description text is 25–80 lines and has no types, no samples, no row counts. That knowledge base is the context pack in §6, keyed by dataset, built once, no model involved.

Q2 · One system prompt or one agent per dataset?

One agent, one system prompt, parameterised by dataset. Every team with a note except Camber does this; Camber's twelve agents differ only in a hand-written per-dataset prompt section — i.e. context, which we generate instead of hand-writing. One agent is also what the loop needs later: one system.md to optimise, one fingerprint per version, one McNemar comparison.

The split that matters is behaviour vs facts: system.md carries how to work (explore, plan, SQL-first, verify, answer contract); the user prompt carries the query and the dataset's context. DABStep-loop already makes exactly this split (agent/prompt.py:build_task_prompt).

So "the dataset is explicit" does not mean a system prompt per dataset. The dataset name selects which context pack is injected; what stays byte-identical across all 54 queries and 12 datasets is system.md, the behaviour file — that is what the fingerprint hashes and what the optimiser later edits.

Where the pack is injected is a separate, smaller choice — and putting it in the system prompt is the better one. The system message the model sees is then system.md + <dataset>/summary.md + the upstream description and hints, and the user message is the question alone, exactly as the benchmark poses it. Nothing is lost: prompt caching keys on the prefix, and the prefix (behaviour + pack) is the same for every trial of a dataset either way; the fingerprint stays sha256(system.md) with the pack's own hash logged beside it as context_sha; Camber's twelve system prompts are the leaderboard precedent that facts in the system slot work. Two things change: facts in the system slot are read as standing instructions rather than as part of the question, which is what we want for "ids carry a '#' prefix"; and the twelve composed system prompts are written into the run folder as agent/system.<dataset>.md so a trace reader sees the exact bytes. D7 below records the choice.

D7 · Which slot carries the dataset's facts? decided: A

Same bytes, same cache prefix, same fingerprint either way; the difference is what the model treats as standing instruction and how clean the user message is. Independent of D1 (how much of the pack is injected).

06 · context pack

6 · Context pack — code generates the facts from the live databases, an agent curates them; one folder per dataset, built once

This is the "file system that gives it knowledge". dab context build opens every store in db_config.yaml, introspects it, and writes data/context/<dataset>/. It is deterministic and committed to git (small: text only), so a run's context is versioned with the code. The upstream description and hints go in verbatim, unedited — that keeps us inside the rubric's "legitimate prompt inputs" and lets the hint file stay a swappable input (v0 without, v1 with).

Two passes: code generates, an agent curates. dab context build is plain code — information_schema, counts, samples, join-overlap measurement — cheap, deterministic, rebuilt after any upstream bump. Then dab context curate runs one curator agent session per dataset (Sonnet 5, effort medium, once; ≈ $1.5 for all 12, traced in MLflow as kind=curate). It reads the generated files plus the upstream description and hints, and writes the two files a model is better at than a template: summary.md — the ~60-line digest that becomes part 2 of the system prompt (D7): which tables matter, the keys and their normalisation, the literal code values, the text columns that will need extraction — and pitfalls.md — the traps in the data, which is what Camber wrote by hand for each of its 12 prompts and Scout generated at run time. Three rules make this legitimate and reproducible: the curator never sees a query (its inputs are data, description and hints — the rubric's own legitimate inputs); its output is committed, so every change is a reviewable diff and context_sha pins which curation a run used; and re-curating is a deliberate bump like re-ingesting, not something a run does. The curator's own prompt, agents/curator/system.md, is the one surface that decides what "curated" means, and it is the third file the loop edits. The line that keeps this honest: a pitfall may describe the data ("ids carry a '#' prefix", "reviews.date is text, not date") and never a question; anything that names a query's answer shape or filter is test-set tuning and is rejected at review, the same rule that separates a general v1 addendum from Permute EQ's per-query evidence (§3). Everything else in the pack — schema, profile, samples, joins — stays generated, so the pack can be rebuilt after an upstream bump without losing the learned part.

One loop, and MLflow traces are its input. The M7 loop is DABStep-loop's shape: evaluate the champion → read the failed trials → propose one edit → evaluate the candidate → McNemar gate → promote or discard. Two things change here. First, a candidate is a version of the three surfaces — system.md, the curator's system.md (re-run to regenerate the twelve summary.md/pitfalls.md), and direct edits to a dataset's pitfalls.md — rendered into twelve composed system prompts at the start of every run, so a curation edit is scored exactly like a behaviour edit: same run, same gate. Second, the optimiser reads failures from the central MLflow rather than from disk: mlflow.search_traces(experiment="dataagentbench/evals", filter="tags.run_id = '…' and tags.passed = '0'") returns every failed trial with its plan turn, every tool span's SQL and error, the verify result and the validator's reason — which is why §10 puts dataset · query · trial · passed · reason · agent · fingerprint · context_sha on every trace as tags, not only on the run. The three surfaces are also registered as MLflow prompts (dataagentbench.system, dataagentbench.curator, dataagentbench.pitfalls.<dataset>; the central server has the DB-backed store the registry needs, and ConvFinQA already uses it), so every run's tags name the prompt versions it ran with and the champion lineage is readable in one place. The run folder is still the record; the registry and the traces are the index the loop queries.

What is in the pack

  • schema.md — per store: tables, columns with types, primary/foreign keys where declared, row counts. The thing the reference agent never had.
  • profile.json — per column: null rate, distinct count, min/max for numerics and dates, top-10 values for low-cardinality text (the values the SQL must match literally).
  • samples/<table>.md — 5 rows per table, wide text truncated at 200 chars.
  • joins.md — measured overlap for every candidate key pair across stores (yelp businessid_1↔businessref_1: how many match after trim/case-fold). Scout's "measured join overlaps".
  • description.txt · hints.txt — upstream files, byte-identical.
  • summary.md — curated: the curator agent's ~60-line digest of the above; becomes part 2 of the system prompt (D7). The rest is read on demand.
  • pitfalls.md — curated: the traps in the data (id prefixes, text-typed dates, duplicate entities, code tables); data facts only, never a question.

How the agent gets it

Two channels. The summary and pitfalls are appended to the system prompt under # Dataset: <ds> (D7) so every trial starts oriented. The full pack is exposed through a read_context(path) tool (and search_context(term)) so the agent pulls depth only where it needs it — LabRat's Cartographer pattern. Both are files on disk the explorer shows on the dataset page, so you can read exactly what the agent will read.

Per-query pre-analysis (Scout's question→column bindings, Permute's evidence layer) is a v2 idea, deferred: it puts a model in the path of a specific question and blurs the general-purpose / benchmark-informed line we want to measure first. The curator is different in kind — it runs once per dataset and never sees a question.

07 · the agent

7 · Agent — v0 is a general-purpose analyst with the right tools and the curated pack; v1 is whatever the loop promotes, and this build ships the loop's scaffolding

Decided in review: this build ships agents/v0/ and measures it. There is no hand-written v1. v1 is the output of the evaluation loop — optimise on the failed trials read from MLflow traces, run the challenger as an experiment, promote it to champion when the gate passes — and that loop is the next build (s02). What this build owes it is the scaffolding: every trial traced with the tags the optimiser filters on (§10), the three prompt surfaces in the central prompt registry (§6), a challenger_of field on every run, dab compare <champion> <challenger> with fixed/broken lists and the McNemar gate, and dab promote that moves the champion pointer and tags the MLflow run. The addendum below is kept as an illustration of what a first challenger will look like — the loop writes it from traces, we do not.

agents/v0/system.md — behaviour only

You are a data analyst answering one question over
several databases. You have a DATABASE CONTEXT and
tools; the stores are read-only and there is no
network.

Work in this order and keep it visible:
1. ORIENT — read the context; describe and sample
   any table you will touch before querying it.
2. PLAN — write the population, the metric, the
   denominator and the answer shape in one short
   block before computing.
3. COMPUTE — aggregate in SQL. Use python only for
   what SQL cannot do. Use llm_extract for free
   text; never regex over prose.
4. VERIFY — run verify() on the result: row counts,
   nulls, uniqueness, plausible range. Re-derive
   the number a second way once. If they differ,
   go back to PLAN.
5. ANSWER — call return_answer with the value only,
   in the shape the question asks for. No prose,
   no audit trail, no units unless asked.

Never guess a column name; never answer without a
query that produced the value.

~200 tokens. agent.yaml freezes model, max_turns 60, tools, effort, timeout 900 s. helper.py exists from v0 (empty) so the optimiser has its surface later.

What a first challenger will look like — the DAB addendum, written by the loop, not by hand

## Conventions for this benchmark
- "above / more than" is strict; "at least" is
  inclusive; "between A and B" is inclusive both ends.
- Exponential moving average: seed with the first
  value, span as stated, computed per group in order.
- Percentages: state the exact denominator in PLAN;
  return a number, not "about".
- Lists: return every item, in the order asked, comma
  separated; names exactly as stored.
- Cross-store joins: check joins.md for the measured
  key and its normalisation (trim, case, "#" prefix).
- Text columns (category, technology area, licence,
  copyright): classify with llm_extract, not regex.
- Read the HINTS as rules of the task, not advice.

Every line is a generalisation of a failure class the field reports (Alkera METHODS.md, Sentinel #73, patents 0→1.00). No query-specific text, no gold values — the rubric's line. This is what makes the row "tuned prompt ✓".

SQLite and DuckDB files go in through DuckDB's postgres extension (ATTACH the file, CREATE TABLE pg.dataagentbench.<ds>_<t> AS SELECT *); Mongo dumps are parsed with bson into a jsonb column plus generated columns for the fields the hints name.

What lands in the schema

Benchmark stores (D6): bookreview_books_info, crmarenapro_accounts … patents_patent_publication, agnews_articles (jsonb), one table per upstream table across the 12 datasets; if two stores in one dataset share a table name the load fails loudly and the rule becomes <dataset>_<store>_<table> for that dataset.

App state: dab_datasets · dab_queries · dab_validators · dab_published_answers · dab_published_verdicts (the index, written by dab ingest alongside the committed JSON) and agent_runs · agent_results · agent_traces (every run, trial, and trace span). agent_results is the record for runs; runs/<id>/ becomes an export (dab runs export) used for MLflow artifacts and the CI gate — a deliberate departure from the siblings' "run folder is the record", because the record is now shared.

Two roles, one schema

dab_owner loads and writes; dab_agent is what the agent's tools connect as: GRANT USAGE ON SCHEMA dataagentbench, SELECT on the benchmark tables only, search_path = dataagentbench, statement_timeout = 60s, no privilege on any other schema. On a shared database this is the line between "one of many apps" and "an agent that can read everyone's data"; tests/test_roles.py proves dab_agent cannot see another schema or write its own.

make db-up starts this project's Postgres (infra/docker-compose.yml, volume dab-pgdata, git-ignored); infra/roles.sql creates the schema and the two roles and is idempotent, so it runs unchanged against central later. The app reads one DATABASE_URL (postgresql://dab_agent:…@localhost:5433/nmp now; central's URI after M8). make platform-up still starts nmp-central-ai's stack, which MLflow needs from the first run.

Sandbox and leak audit

execute_python runs in a python:3.12-slim container with --network none — no route to anything, Postgres included. Data reaches it through a per-trial /work volume: query_db(sql, save_as="x.parquet") writes results there and the code reads them with pandas or duckdb, so Python never holds a database credential and the read-only role is the only way in. One container per run, a fresh kernel per trial (D3). After every run dab audit <run> greps traces for URLs, ground_truth, validate.py, docs/data, other runs' ids and any schema name other than dataagentbench, and fails the run if one appears.

Re-hosting the stores is leaderboard precedent — Permute Core runs "DuckDB over Parquet-normalised stores" (PR #85, 0.84) — but it is a change from the rubric's sanctioned files; a submission would say so in its PR as Permute did.

11 · token profile

11 · Tokens — a trial's cost is quadratic in turns, and turns are the only number we do not yet know

Every turn re-reads the whole conversation, so input tokens grow as T·P + h·T(T−1)/2: P the fixed prefix (system prompt + query + context summary + tool schemas), h what one turn adds (the model's output plus the tool result), T the turns. The model below is calibrated on DABStep-loop's measured Haiku 4.5 runs (runs/20260915T080017Z_v2_dev_haiku_lean: prefix 2.7k, median 5.5 turns, 29.5k input, 2.7k output, $0.035 per question) and then pushed to DAB's longer trials. Same effort (medium) and same turns for all three models, so the bands differ only by price.

P ≈ 3 000prefix tokens per call: system.md ~300 + query ~80 + context summary ~1 500 + 9 tool schemas ~1 100 (DABStep measured 2.7k with 1 tool)
h ≈ 1 000added per turn: ~300 output (plan text + tool call) + ~700 tool result (a 200-row page, a describe, a verify)
T ≈ 20 medianturns per DAB trial, from Phoenix-CLI's 3 493 Bash calls / 270 trials ≈ 13 tool calls plus orient/plan/verify turns; p90 ≈ 40; cap 60
0.1× / 1.25×cache read / cache write price vs input; the Agent SDK caches the prefix and history automatically, so ~90 % of input is read at 0.1×

What the Max 5× window holds — measured from your own 14 limit hits

Anthropic does not publish the window in tokens, and productivity-tracker derives USD rather than observing the limit. But the transcripts under ~/.claude/projects record every 429 rate_limit with rateLimitType: five_hour and its resetsAt, so the window's start is resetsAt − 5 h and its size is everything sent between that and the first rejection. Fourteen windows hit the limit between 2026-09-02 and 2026-09-21 (1 616 rejected requests). Priced at the tracker's rates, the spend at the moment of the hit was $41 – $182 derived, median $108 — a 4× spread, which says the limit is not dollar-denominated.

The spread sorts by model: the two Haiku-dominated windows (2026-09-15 12:00 and 17:00 UTC, 60–80 % Haiku by spend) hit at $44 and $41; mixed Opus/Sonnet/Fable windows at $70–$122; the Opus-heavy ones at $159–$182. A weighted-token fit over the 14 hits (best coefficient of variation 0.25, against 0.43 for derived dollars) puts Haiku's weight equal to Opus's, output ≈ 5× input, cache reads ≈ 0.1× — i.e. the plan counts Haiku tokens as if they were Opus tokens, so cheap-per-dollar work is not cheap-per-window. The table therefore divides each column by the window size observed for that model family: Haiku $42 · Sonnet $108 · Opus $170. Those are your measured numbers, not a plan sheet; dab runs profile re-fits them from the smoke.

BILLING=subscription by default via the Claude CLI, with subscription_env() blanking ANTHROPIC_API_KEY in the SDK child so a run started inside Claude Code cannot bill against it. llm_extract uses Haiku 4.5 through the same path. .env.example gains MLFLOW_TRACKING_URI (D5) and MLFLOW_DISABLE_AGENT_HINT=1, as the siblings.

CLAUDE.md's "this build calls no model" rule is retired by this plan; the replacement rule is "a model is named in one file and every run records it".

Budget, from §11 and the field

  • Haiku 4.5, effort medium, blended $0.13 per trial: smoke 12 × 1 ≈ $1.6 · v0 wide 54 × 1 ≈ $7 · 54 × 5 ≈ $35 per agent version; all four steps ≈ $79.
  • The same turns on Sonnet 5 ≈ 2×, on Opus 5 ≈ 5× (§11 table) — a later decision once Haiku's measured profile and pass rate are in.
  • Field reference: DataTrail $3.58 for 270 trials; upstream GPT-5-mini $67 for 2 700; Kimi-K2 $1 304 for 2 700 at 100 iterations.
  • Context build: $0 (no model). llm_extract on Haiku: cents per dataset, cached by hash.

D4 · Billing decided: A — subscription via the Agent SDK, like the siblings — model is decided Haiku 4.5 · effort medium

The SDK reports cost_usd and the four token counts on subscription too, so the profile is measured either way; the choice is only whose bill it lands on.
