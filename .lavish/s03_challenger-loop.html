01 · goal

Done for C1 means two arms, same queries, same trials — and a verdict with its denominator, written down next to the challenger

The champion's numbers today come from one trial per query. A challenger can only be judged against the champion when both are re-run on the same queries with the same number of trials. So every screen runs two arms: the champion again (the baseline) and the challenger. Each result is passed/n per query, and the verdict goes into the challenger's own folder, so the lineage of edits can be read in git.

Where the redundancy comes from

  • No cache at any level. Each 40-row batch starts a new SDK session. The same article gets labelled again for every query, every trial and every arm. A k = 3 agnews screen would label the same titles 6 times.
  • Same column, different questions. pancancer/2 and /3 extracted the barcode from the same 1,088 rows twice.
  • A model where SQL suffices. 5 of the 11 trials used it for a pattern or keyword job: the barcode (twice), star counts, copyright lines, a "massage" filter.
  • One column per call. Classification that needs title and description got the title only.
  • One call at a time. 50 sequential sessions for 2,000 rows is what uses up the 900 s.

What the leaderboard did with text columns

From each row's maintainer note in data/index/leaderboard.json (verified this session):

  • Scout 0.906: LLM-backed extract_fields and classify_aggregate. The second labels and counts in one call, so the agent receives the counts, not 14,000 labels.
  • LabRat 0.802: local-embedding classification, no LLM call per row, plus a result ledger so results are reused rather than recomputed.
  • Stela 0.811: "model-backed semantic operators" (map, filter, classify as query operators).
  • DataTrail 0.820: no extraction tool; a prompt rule to "extract entity names from prose description fields".
  • The agnews wall pushes agents to cheat: Sentinel's traces show label-fetch attempts (blocked); fabric-rlm lost 8 agnews trials for loading the HuggingFace gold labels.
  • Published agnews: q1 35/270 (Opus ReAct 5/5), q2 15/270, q3 0/270, q4 58/270.

C1b becomes c02-extract: six changes, ordered by what the audit shows

  1. SQL first. Replace system.md:17 ("rather than string matching") with the opposite order. The tool description and the rule then say: if the value follows a pattern (ids, numbers after a word, literal tokens), use substring(… from 're') in query_db; call llm_extract only when the answer depends on meaning. This covers 5 of the 11 trials.
  2. Several columns in. columns: ["title","description"] in place of column, with the instruction applied to all of them joined together.
  3. Run batches concurrently. Batches go out in parallel, capped (e.g. 8 at once), and are larger for short texts. Titles are ~10 words, so 200 per call is fine. Target: 15,000 rows well within 900 s.
  4. Label and count in one call (Scout's classify_aggregate): group_by and stop_when options. q4 gets counts per region; q1 labels in length order and stops at the first Sports article.
  5. Cache within a trial, keyed by (instruction, text hash), so a retry or a second call on overlapping rows reuses the labels. Whether the cache lasts across trials is D16.
  6. Honest accounting. Extract tokens are recorded by kind (the caveat on the agnews card), and every call records rows · labelled · cached · seconds on its tool span, so the replay shows the cost.

D16 · How far does the label cache reach? withdrawn · llm_extract is removed

The cheaper the cache, the less independent the trials are. The leaderboard's Pass@1 treats each of the 5 trials as an independent attempt.

03e · embeddings for the text fields — your note on LabRat, the classifier later

An embedding per prose row can be built locally in minutes for about 180k rows, with no model call per row at question time, but on its own it doesn't label anything: agnews/2 and /3 still need the classifier you've parked

LabRat (0.802) classified text with local embeddings instead of an LLM call per row. Here, every prose column in dataagentbench gets a vector built once by dab data embed. It's code, it never sees a question, and the same model embeds the agent's search text inside a tool. That makes it the same kind of thing as the context pack: derived only from the sanctioned data and blind to the questions, so it's legitimate by construction.

How Postgres fits in: it stores the vectors and does the retrieval; it doesn't make embeddings

StepWhenWho does it
1 · encode every prose rowOffline, once: dab data embedThe local encoder (bge-small) in Python reads the rows as dab_owner and writes vector(384) rows into dab. Postgres only stores them.
2 · indexOffline, oncePostgres: CREATE INDEX … USING hnsw (emb vector_cosine_ops). pgvector 0.8.2 does this.
3 · encode the agent's search textIn the trial, per callThe same encoder, inside the semantic_search tool: one short string, a few milliseconds, no API.
4 · retrieveIn the trial, per callPostgres: ORDER BY emb <=> $1 LIMIT k (cosine distance) through the HNSW index, as dab_agent, joinable to any other table in the same query.

That is your "embedding done in the database offline; the agent uses the encoder and does retrieval". pgvector is storage, distance operators and indexes only. Extensions that call a model from inside SQL (pgai, PostgresML) exist but aren't installed. They would put a model inside the database, which the platform doesn't need.

Measured, not guessed

BAAI/bge-small-en-v1.5 (384 dimensions, ONNX via fastembed, CPU, no key) on 2,000 agnews title || '. ' || description rows on this Mac: 39 texts/s on one core, 9 s to load. So agnews alone is ≈ 55 min on one core, and all ≈ 180k v1 rows ≈ 77 min. Across the 10 cores I estimate 10–15 min, but I haven't measured it: my parallel probe hung without the __main__ guard multiprocessing needs on macOS. It's a one-off build, re-run only when the data or the model changes.

What the agent gets

  • semantic_search(table, column, text, k, where?) embeds text with the same model, then runs ORDER BY emb <=> $1 LIMIT k over an HNSW index as dab_agent. It returns keys, distances and a snippet.
  • similar_to(table, key, k): rows nearest to a given row, for spotting duplicates and near-duplicates.
  • SQL can join to the vectors directly (<=> between two stored rows) with no tool.
  • The table list in the prompt marks which columns have embeddings. describe_table and sample_rows never print a vector.

What it changes elsewhere in the plan

  • A fourth thing that runs a model. CLAUDE.md says three things call a model, all through the Agent SDK. A local embedding model is a different kind (no key, no subscription, deterministic), but the rule should name it: "…and the local embedding model in dab data embed and semantic_search, pinned by name and revision."
  • Goldens can use it. The same text and model give the same vector, so a semantic_search step replays exactly, unlike llm_extract (D18). The toolset fingerprint (C2) must hash the model name and revision.
  • A new challenger, c07-embed: v0's belt plus the two tools, screened on agnews like any other. My honest expectation: it helps find rows by topic ("articles about football") and cuts llm_extract calls. It doesn't produce the category counts agnews/2 and /3 are graded on. That's the classifier, which comes later, per your note.
  • Downstream, parked: a classifier over these vectors, either zero-shot against label descriptions or trained on labels the agent assigns to a sample. That's where agnews/2–3 could move. It isn't in this plan's milestones.

The case for pythonDoes it hold here?
Fuzzy entity resolutionYes, the one real gap. music_brainz stores one song four ways across sources: "Street Hype" / "Street Hype - Groove City" / "StreetH ype (Groove City)" / "011-Street Hype", by "Brucqe Maginnis" and "Bruce Maginnis". Python has rapidfuzz. Permute EQ got music_brainz 15/15 with no python because DuckDB has jaro_winkler_similarity and levenshtein built in. Our Postgres ships the equivalents, pg_trgm (similarity(), %) and fuzzystrmatch (levenshtein()). Both are available but not installed on dab. Fix: add them to dab's extensions in the platform registry and run db-init. It's a platform change, so I haven't done it.
Maths Haiku gets wrong in SQLA risk, not a need. A recursive EMA CTE is harder to write than pandas.ewm. The SQL-only entries ran Opus 5 at max reasoning, and Haiku is weaker. That's why c08-sqlonly is a screen. If the EMA queries break, the answer is a pitfall or a golden-SQL pattern, not a python tool.
Joining across database enginesNot here. Upstream, the data sits in Postgres, SQLite, DuckDB and MongoDB, and python is the glue. We loaded all of it into one Postgres, which removes the main reason the reference agent had python.
Statistics librariesNot in the 54. pancancer/3 asks for the chi-square statistic, not a p-value; nothing asks for a fitted model or a test's p.

04 · the loop

Six steps round, kept light: a challenger is promoted after one 54 × 1 run if a one-sided McNemar test says it's better, or if it gains with no question lost

deferred · your call Golden SQL comes first. If goldens can be written in Postgres for the questions, the loop gets revisited with them in hand. The golden SQL stand-up is built (42fedcb, §6 and the Golden tab); nothing else in this section is.

The gate, as you set it: champion and challenger each run all 54 once. Let b be the questions the challenger fixed and c the ones it broke. Promote if the one-sided exact McNemar p = P(X ≥ b | b + c, ½) < 0.05, or if b > 0 and c = 0. One caution from our own runs: the same v0 went 5/12 → 7/12 on 12 common questions from trial noise alone, so at k = 1 "no question lost" can happen by luck. The gate stays as you set it, and the Runs compare view shows b and c for every pair.

This is the loop s01 §6 described (after DABStep-loop), with two additions: a golden set that says which part of a failed trial went wrong, and a leak check between a proposal and the challenger it becomes. With the gate at 54 × 1, one full run uses about 17 % of a Max 5× window (s01 §11 measured 54 × 5 at about 83 %), so a gate costs about a third of a window.

  1. Screen. dab eval --agent champion --datasets agnews --trials k and the same with --agent c01-hints --challenger-of <that run>. Same queries, same k. Both runs are labelled screen on the Runs board and never become champion.
  2. Score. dab compare <baseline> <challenger>: passed/n per query for each arm, which queries the challenger fixed and which it broke, and the difference in pass rate with a 95 % confidence interval. On 4–7 queries that interval is wide, so a screen can rank candidates but never promote one.
  3. Diagnose. dab runs golden <run> compares each trial with its query's verified golden and puts every failure in one class (§7). Written to runs/<id>/golden.jsonl, so the run folder stays the record.
  4. Propose. A proposer reads the failure classes and the current files and writes one edit to one file, with a one-paragraph reason (§8).
  5. Leak check. Rejects any edit that contains 5+ consecutive words from a question, a gold value, or a literal from a golden's SQL. Same idea as tests/test_context.py, which already does this for the curated files.
  6. Challenger. agents/cNN/ = the parent version plus the edit; parent and change in agent.yaml record where it came from; NOTES.md records the screens and their verdicts.

06 · the Golden tab

A Golden tab where you build each golden trace step by step, using only one agent version's tools, and every golden can be re-run exactly

pivoted · built · 42fedcb, d32d602 A golden is now the SQL on the Postgres DB that recreates the answer, and you write each one. The Golden tab is live. Per question: write SQL, run it as dab_agent (read-only, 60 s, only the agent's tables), then see two checks. One is the question's validator. The other is whether the result recreates the gold text itself (exact, or the same rows with different column names or order). Saves are kept in dataagentbench_meta.golden_sql, which the agent can't read, and the tab starts at 0/54. Superseded below: step-by-step golden traces, per-version tool lists, replay digests, D17 and D18. The rest of this section is kept only as the record of the earlier design.

You have the gold answer for all 54 questions but not the tool calls that reach it. A golden trace is those calls: an ordered list of steps, each a real tool call with its input and recorded output, ending in an answer that the question's own validator passes. You curate them in a new Golden tab. The rules below are the ones you set:

The four rules

  1. Starts empty. 0/54. Nothing is seeded automatically. "Start from a trial" is a button that pre-fills the builder when you choose to use it; nothing is saved until you save.
  2. Only that version's tools. You pick an agent version first. The step's tool list is exactly that version's agent.yaml tools, with the same schemas. A golden for v0 can't use a tool v0 doesn't have.
  3. Re-runnable exactly. dab golden replay <query> --version v0 runs every step through call_tool, the same code path a trial and the playground use, with the recorded inputs, and checks each output against its recorded digest. The replay passes when every step matches and the answer passes the validator.
  4. Changes as the tools change. Each golden records the version, model and toolset fingerprint it was built with. When a later version changes a tool, the goldens that use that tool are flagged as out of date for that version, naming the step. Goldens that don't use it still apply (D17).

The toolset fingerprint — this has to exist first

Today a version's fingerprint hashes system.md, helper.py and agent.yaml (versions.py:19–20). Tool code lives in src/, so c02-extract could change llm_extract and every version would keep the same fingerprint. The golden needs a hash that changes when a tool's code does:

  • per tool: sha256 of its name, description, JSON schema, the source of its body function, the module constants it reads (e.g. EXTRACT_BATCH) and, for a tool that calls a model, the model id
  • per version: the hash of its tools' hashes, in agent.yaml order → toolset_sha
  • written on every run (run.json) as well as every golden, so two runs can be compared tool for tool

What "exactly" can mean for a model step: query_db, describe_table, context, execute_python and verify are deterministic, given the fixed row order from c05-belt. llm_extract is not: the same prompt to Haiku can give different labels. D18 decides how a golden handles that.

08 · the proposer

The proposer can edit five surfaces, sees failure classes rather than answers, and every edit passes a leak check before it becomes a challenger

paused · your call Nothing here gets built until golden SQL has been written and you've refreshed the plan.

This is the part that "gets the agent to propose updated prompts and files". It is the easiest place to fool yourself: a proposer that sees the gold answers will write rules that fit the test set, which is the "tuned prompt" pattern s01 §3 excludes. So the design limits what the proposer reads as well as what it writes.

reads

  • the screen's dab compare output: pass/n per query, fixed, broken
  • golden.jsonl: each failure's class, the tables it read vs the golden's, and where it first diverged
  • the failed trials' own traces (the agent's plan, SQL and errors)
  • the current files it is allowed to edit and their edit history in NOTES.md
  • not gold values, golden SQL text, or validator source code (D15)

may edit — one per challenger

  • system.md — how the agent works (answer rules, checks before answering)
  • data/context/<ds>/pitfalls.md — facts about the data only
  • agents/curator/system.md → re-curate one dataset
  • agent.yaml settings: hints, max_turns, effort
  • a tool change (e.g. llm_extract limits) only as a proposal — you approve code changes

rejected by the leak check

  • 5+ consecutive words from any of the 54 questions
  • any gold value (numbers matched with tolerance, strings case-insensitively)
  • any literal from a golden's SQL ('Indianapolis', 'Amy Jones')
  • more than one file changed
  • Runs in dab challenger new and in CI, like tests/test_context.py
