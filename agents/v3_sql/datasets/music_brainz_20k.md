## Matching songs/artists in `music_brainz_20k_tracks` (entity resolution)
- A raw case-insensitive substring match on `title`/`artist` is NOT enough: rows can have extra internal spaces or stray characters inside the words themselves (e.g. "StreetH ype (Groove City)" for "Street Hype"), not just the known per-source wrapping (album suffix, "Artist - Title", leading digit code). A plain LIKE on the lower-cased raw column will miss such rows and silently return a partial/wrong set of duplicate track_ids.
- Correct approach: for both the question's title/artist text and the table's title/artist columns, build a "letters-only" comparison key by removing every character that is not a letter (regex character class matching non-alphabetic characters, replaced globally with an empty string), then lower-case the result, then compare the keys with substring matching. Comparing on the letters-only key catches spacing/punctuation noise that survives simple lower-casing alone.
- Do this letters-only normalization in addition to, not instead of, the per-source unwrapping (source_id 1 "Title (Album)", 2 "Artist - Title" with artist NULL, 3 "Title - Album" with album NULL, 4 leading digit-code prefix, 5 plain but with minor typos/spacing). Skipping either step undercounts the duplicate track_id set.
- A song/artist named in a question is one real-world entity spread across up to 5 track_id rows (one per source_id, occasionally fewer if a source variant has no matching text). Always resolve to the FULL set of matching track_ids before joining to `music_brainz_20k_sales`; summing/grouping revenue over only some of the matched track_ids undercounts totals and can change which store/country ranks highest.
- When the question asks "which X earned the most", return only the requested identifying column, not extra aggregate columns, unless the question also asks to show the amount.
