- Star/fork/other repo metrics live ONLY as free text in `deps_dev_v1_project_info."Project_Information"`, never as separate numeric columns. Extract the `owner/repo` slug from that text with a regex like `[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]*[A-Za-z0-9_-]`, lowercase it, and join to lowercased `deps_dev_v1_project_packageversion."ProjectName"`. Don't match Project_Information to ProjectName via LIKE/substring on the whole text blob.
- Fork counts appear in three mutually exclusive phrasings that together cover every row (checked: 154 + 68 + 548 = 770 rows): a "forks count of N" style, a "forked N times" style, and a plain "N forks" style. Try all three (case-insensitive) before trusting one, strip thousands commas, cast to a number. Star counts and other metrics likely have similarly varied phrasings worth surveying first.
- `Licenses` and `VersionInfo` columns are JSON stored as text, sometimes pretty-printed across lines. Parse as JSON (`::jsonb`, `?`, `@>`) rather than substring/LIKE, which can miss whitespace variants.
- One GitHub project maps to many package versions in `project_packageversion`/`packageinfo`. When a question asks for "the" package/release/version for a project (not just its metric), don't collapse the many matching rows with `DISTINCT` and drop the Version column — pick one row per project (rank by most recent `UpstreamPublishedAt`, then `VersionInfo`'s `Ordinal`, then `Version` string) and include that row's `System`, `Name`, and `Version` columns in the final output alongside the metric, since the identifying version is itself part of what's being asked for.
- Join path: `packageinfo(System,Name,Version)` = `project_packageversion(System,Name,Version)`; `project_packageversion.ProjectName` equals the slug extracted from `project_info.Project_Information`, not a free-text search match.
