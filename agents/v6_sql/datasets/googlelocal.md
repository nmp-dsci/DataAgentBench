- `googlelocal_business_description.name`/`description` rarely say "massage" literally: descriptions are paraphrased, e.g. "skilled therapists offer soothing treatments", "expert bodywork services", "therapeutic bodywork services", "rejuvenating therapies and soothing body treatments". To find a trade (massage, spa, etc.) match BOTH `name` and `description` with a broad regex covering synonyms (bodywork, body treatment(s), therapy/therapist/therapeutic, massage), not just `name LIKE '%word%'`. Before trusting a keyword pattern, survey how many of the 79 rows it catches and eyeball matches and near-misses.
- When averaging ratings, keep the underlying aggregate at full numeric precision for any filtering (HAVING/WHERE) and ordering (ORDER BY); only round for display in the outer/final select. Rounding first can change which rows pass a threshold and can tie-break rows in the wrong order.
- Averages of `googlelocal_review.rating` are often exact whole numbers (e.g. one 5-star review averages to exactly 5). A plain `numeric`/`round(...)` value for a whole number can render without any decimal point (e.g. "5" instead of "5.00"), breaking a grader expecting a decimal score. Cast the final displayed rating average explicitly to `text` (e.g. `round(avg_rating, 2)::text`) so a decimal point is always present, but sort/filter on the underlying numeric column, not the text one.
- `googlelocal_review.time` mixes several text formats in one column, e.g. "September 03, 2020 at 04:15 PM", "2021-04-12 17:07:52", "08 Mar 2020, 00:04". A `LIKE '%2019%'` on the 4-digit year works across all of them, but extracting month/day or casting to timestamp requires handling each layout separately.
- Join `googlelocal_review` to `googlelocal_business_description` only on `gmap_id`; business names can repeat or differ in casing/spacing, so never join or filter on `name` as the key.
