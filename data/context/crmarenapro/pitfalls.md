- `crmarenapro_*` any `Id`/foreign-key column: ~25% of ID-like values carry a leading `#` (per hints.txt); strip it before joining or filtering, e.g. `#001Wt00000PFj4zIAD` vs `001Wt00000PFj4zIAD` in `crmarenapro_account."Id"`.
- `crmarenapro_task."Status"`, `crmarenapro_case.status`, `crmarenapro_lead."Status"`, `crmarenapro_opportunity."StageName"`, `crmarenapro_quote."Status"`, `crmarenapro_order."Status"`, `crmarenapro_contract."Status"`: values have variable trailing whitespace treated as distinct strings in profile.json (e.g. "Not Started", "Not Started ", "Not Started  " are 3 separate distinct values); trim before matching exact literals.
- `crmarenapro_task."Status"` has 15 distinct raw values collapsing to only 5 semantic states (Not Started/In Progress/Deferred/Waiting/plus dupes) — do not treat distinct count as number of real statuses.
- All date/time columns across every table are `character varying`/`text`, not native date types (e.g. `crmarenapro_task."ActivityDate"`, `crmarenapro_opportunity."CreatedDate"`, `crmarenapro_case.createddate`) — must `CAST`/`::date` or `::timestamp` explicitly.
- `crmarenapro_lead."CreatedDate"` is a full timestamp (`2021-03-14T07:26:24.000+0000`) but `crmarenapro_lead."ConvertedDate"` is date-only (`2021-04-02`) — the two "date" columns on the same table have different granularity.
- `crmarenapro_lead."ConvertedContactId"`/`"ConvertedAccountId"`/`"ConvertedDate"` are NULL for ~39.59% of rows (null_rate 0.3959) — null means the lead was never converted, consistent with `"IsConverted"=0`; don't assume missing = data error.
- `crmarenapro_case.closeddate` is NULL for ~51% of rows — null means the case is still open (not yet closed), not missing data.
- `crmarenapro_voicecalltranscript__c."LeadId__c"` is null for 85.64% of rows and `"OpportunityId__c"` is null for 14.36% — most transcripts link to an opportunity, not a lead; check which FK is populated before joining.
- `crmarenapro_livechattranscript.contactid` is NULL for 100% of rows (null_rate 1.0) — this column is entirely empty; do not join on it.
- `crmarenapro_pricebook2."ValidFrom"`/`"ValidTo"` are NULL for 100% of rows — entirely empty columns despite existing in the schema.
- `crmarenapro_opportunity."ContractID__c"` is NULL for ~86% of rows — most opportunities have no linked contract; treat absence as normal, not an error.
- `crmarenapro_product2."External_ID__c"` is not a simple external id: it's a composite string of comma-separated category names plus an underscore-numeric suffix (e.g. "AI-Powered Circuit Design Tools,Cloud-Based Design Collaboration_47"); parsing is required to extract categories or the numeric part.
- `crmarenapro_emailmessage.toids` looks like a scalar text column but stores a JSON-array-formatted string of recipient ids (e.g. `["005Wt000003NJBVIA4"]`); it is plain text, not JSONB, so `->>` does not apply — string parsing is needed.
- `crmarenapro_emailmessage.parentid` is NULL for ~91% of rows — mostly empty; `relatedtoid` is the more consistently populated relationship column.
- `crmarenapro_orderitem."Quantity"`, `"UnitPrice"`, `crmarenapro_opportunitylineitem."Quantity"`/`"TotalPrice"`, `crmarenapro_quotelineitem."Quantity"`/`"UnitPrice"`/`"Discount"`/`"TotalPrice"` are all stored as `character varying` text, not numeric — must be cast before arithmetic.
- `crmarenapro_opportunity."Amount"` is a genuine double precision numeric (min 2309.94, max 297493.625), unlike the other line-item money columns which are text — don't assume a uniform pattern across tables.
- `crmarenapro_opportunity."Id"` ↔ `crmarenapro_quote."OpportunityId"` join is measurably weak even after normalisation (normalised share only 0.6017 per joins.md) — a meaningful share of quotes cannot be matched to an opportunity by this key.
- `crmarenapro_contact."Id"` ↔ `crmarenapro_case.contactid` join is unreliable (normalised share only 0.0813) — do not rely on this pair to link cases to contacts.
- Account-id joins into support tables (`crmarenapro_case.accountid`, `crmarenapro_livechattranscript.accountid`) top out at normalised shares of ~0.53 and ~0.43 respectively — a large share of support records cannot be matched to `crmarenapro_account."Id"` by account id alone.
- `crmarenapro_user."FirstName"` is NULL for some system/integration rows (e.g. rows with LastName "Integration User", "Platform Integration User", "Chatter Expert") — these are non-human service accounts, not analysts' sales reps.
- `crmarenapro_case.id`, `.issueid__c`, and other id columns in the `support` store use lowercase column names (`id`, `accountid`, `ownerid`) unlike the CamelCase `"Id"`, `"AccountId"`, `"OwnerId"` used in other stores — quoting/casing differs by store.
- `crmarenapro_pricebookentry."Id"` ↔ `crmarenapro_opportunitylineitem."PricebookEntryId"` overlap tops out at normalised share 0.92, not 1.0 — a portion of opportunity line items reference pricebook entries not present (even after cleaning) in `crmarenapro_pricebookentry`.
- `crmarenapro_product2."Id"` ↔ `crmarenapro_quotelineitem."Product2Id"`/`crmarenapro_opportunitylineitem."Product2Id"` normalised shares are 0.8627/0.902 — not all line-item products resolve to a `crmarenapro_product2` row even after `#`-strip/trim.
- `crmarenapro_territory2."Description"` contains comma-separated US state abbreviations (e.g. "MO,KS,OK"), not free narrative text like other `Description` columns — its content and format differs from every other `Description` column in the dataset.
- `crmarenapro_livechattranscript.body` and `crmarenapro_voicecalltranscript__c."Body__c"` embed HTML entities (e.g. `&#39;` for apostrophe) inside otherwise plain-text transcripts.
