- `pancancer_atlas_clinical_info.patient_id` stores only the trailing numeric segment of the TCGA barcode (e.g. `1953`, `0933`), not the full barcode — it will not directly join to `ParticipantBarcode`-style columns in the molecular tables.
- `pancancer_atlas_clinical_info.Patient_description` is the only column holding the full barcode, gender, vital status and UUID, but it's a free-text sentence with varying templates (samples show at least three distinct phrasings) — values must be extracted, not filtered with a simple `=`.
- There is no measured/verified join overlap between `pancancer_atlas_clinical_info` and either molecular table; joins.md only reports overlap between `pancancer_atlas_mutation_data."ParticipantBarcode"` and `pancancer_atlas_rnaseq_expression."ParticipantBarcode"`.
- `pancancer_atlas_mutation_data."ParticipantBarcode"` vs `pancancer_atlas_rnaseq_expression."ParticipantBarcode"` only overlap ~50% (raw share 0.5034), and normalising (trim/strip/lower-case, digits-only) barely improves it (0.5092 / 0.5204) — roughly half of participants in one table have no counterpart in the other; this is a real coverage gap, not a formatting issue.
- `pancancer_atlas_clinical_info.days_to_death`, `.days_to_last_followup`, `.days_to_new_tumor_event_after_initial_treatment`, `.number_of_lymphnodes_positive`, `.lymph_node_examined_count`, `.karnofsky_performance_score`, `.eastern_cancer_oncology_group` are all typed `text` and mix numeric strings (e.g. `"943.0"`, `"0"`, `"00"`, `"01"`) with sentinel strings (`[Not Applicable]`, `[Unknown]`) — casting requires filtering out non-numeric sentinels first.
- `pancancer_atlas_clinical_info.form_completion_date` is text, not a date type, and is not zero-padded (`2009-10-20` vs `2009-6-2`), so lexical sorting/comparison will not match chronological order.
- Categorical columns across `pancancer_atlas_clinical_info` (e.g. `race`, `pathologic_stage`, `tissue_retrospective_collection_indicator`, `new_tumor_event_after_initial_treatment`) use bracketed sentinel strings `[Not Applicable]`, `[Unknown]`, `[Not Evaluated]`, `[Discrepancy]` as literal values, not SQL NULL — a `WHERE col IS NOT NULL` will still include these placeholders.
- `pancancer_atlas_clinical_info.informed_consent_verified` has only one distinct value (`YES`, 10,761 rows) — it carries no discriminating information despite looking like a yes/no flag.
- `pancancer_atlas_mutation_data."HGVSp_Short"` contains the literal string `.` (a single period) rather than NULL when there is no protein-level annotation, e.g. seen alongside `Variant_Classification = 'Splice_Site'`.
- `pancancer_atlas_mutation_data."CENTERS"` and `"FILTER"` can hold multiple pipe- or comma-joined values in one field (e.g. `INDELOCATOR|VARSCANI`, `common_in_exac,wga`), so an exact `=` match against a single center/filter name will miss combined-value rows.
- `pancancer_atlas_rnaseq_expression.normalized_count` has a small negative minimum (`-0.897254599378421`) despite being a "normalized count," and 1.72% null rate — `log10(normalized_count + 1)` per the hint formula will error or return NaN for values below -1, though none observed are that low.
- `pancancer_atlas_rnaseq_expression."Entrez"` is typed `bigint` in schema.md even though description.txt calls it a string — treat it as numeric, not text, when joining or filtering.
- `pancancer_atlas_clinical_info.race` and `.ethnicity` have high null rates (9.32% and 16.6%) plus additional `[Not Evaluated]`/`[Unknown]` placeholder rows on top of true nulls, so "unknown race" can appear three different ways (NULL, `[Not Evaluated]`, `[Unknown]`).
- `pancancer_atlas_clinical_info` column names for breast-, lung-, and glioma-specific fields (e.g. `breast_carcinoma_estrogen_receptor_status`, `egfr_mutation_performed`, `kras_gene_analysis_performed`) are populated only for the relevant cancer subset — null rates above 85–95% reflect not-applicable-to-this-cancer-type rather than missing data.
- `pancancer_atlas_mutation_data` and `pancancer_atlas_rnaseq_expression` each have multiple barcode granularities (Participant, Sample, Aliquot) that are almost-but-not-exactly nested prefixes of one another (e.g. `ParticipantBarcode` = `TCGA-06-0675`, `SampleBarcode` = `TCGA-06-0675-11A`, `AliquotBarcode` = `TCGA-06-0675-11A-32R-A36H-07`) — picking the wrong granularity for a join or count will over- or under-count.
- `pancancer_atlas_clinical_info.number_of_lymphnodes_positive_by_he`, `_by_ihc`, and `.total_pelv_lnr`/`.total_aor_lnr` have very high null rates (63.7%–94.9%) — these are sparse, cancer-subtype-specific measures, not general-purpose lymph node counts.
- No timezone information is given for any date/time-like field; `days_to_*` columns are relative day-offsets (can be negative, e.g. `days_to_birth` ranges -32918 to -3982), not calendar dates.
